# Council — POM-RX Core Exact Authorization and Single-Use Gate

Status: `PROPOSED / TIER_B / HUMAN_REVIEW_REQUIRED`

Date: 2026-08-19

Baseline: `8b8630c124bbf37d2919aa008e4f7f587f5c92f2`

## Decision objective

Define the smallest common POM-RX Core contract that can later turn a bounded, witnessed preflight into one exact, short-lived execution authority and make an execution-side Gate consume that authority at most once.

This council does **not** authorize a live wallet, payment, exchange, API mutation, testnet transaction or mainnet transaction. It defines common semantics so application blocks such as Wallet Guard do not invent incompatible authorization, expiry or replay rules.

## Current evidence boundary

The merged strict verifier can now produce bounded structural verdicts for `pom-rx-v0.1/strict-errata-1`, but every strict verdict remains non-authorizing. Signed source/witness primitives also exist, but enrollment, revocation, trusted time and durable witness-service semantics remain incomplete.

Therefore the Core may specify and test the Gate state machine now, but a production authorization issuer remains blocked until the witness trust lifecycle is separately proved.

## Shared Core rule

Exact authorization and Gate consumption belong to POM-RX Core. Application blocks may define domain-specific intent/context commitments and downstream adapters, but they must not fork or duplicate:

- capability lifecycle;
- expiration semantics;
- replay semantics;
- exact commitment comparison;
- Gate state transitions;
- authorization-result vocabulary;
- fail-closed behavior.

## Exact authorization binding

The generic Core capability binds an application action and its trusted execution context through commitments rather than chain-specific fields.

Minimum binding:

```text
schema_version = pom-rx-exact-authorization/0.1
capability_id
binding_profile
run_id
agent_ref
subject_ref
method_hash
policy_hash
action_commitment
context_commitment
preflight_receipt_hash
witness_ack_hash
source_key_id
witness_key_id
verification_profile
verifier_version
implementation_artifact_sha256
effective_verification_policy_sha256
issued_at
expires_at
```

`binding_profile` is an exact versioned application normalization identifier. It prevents one application's action/context commitment from being reinterpreted under another application's semantics.

`action_commitment` binds the exact normalized requested action. `context_commitment` binds trusted execution context that the application must freshly observe before forwarding. For Wallet Guard this context must cover the trusted origin, active chain, active account, RPC method and the normalized request identity/effects required by its ADR.

The strict-verifier profile/version/artifact digest and effective verification-policy digest are copied from the bound strict verdict so the later authorization cannot silently lose the exact verifier/policy identity that justified its structural prerequisite.

The Core does not interpret EVM origin/account/spender/recipient semantics. The Wallet Guard application owns that normalization and provides a versioned `binding_profile` implementation to the common Gate bootstrap.

## Commitment domains

Application action/context commitments require explicit domain separation chosen by the ratified application profile. Cross-profile reuse of one generic raw hash domain is forbidden.

The full verified witness acknowledgement is committed as:

```text
SHA-256(
  UTF8("swisstokint:pom-rx-witness-ack-record:v1:") ||
  UTF8(canonical_witness_ack)
)
```

The exact-authorization binding commitment is derived, not stored inside its own record:

```text
SHA-256(
  UTF8("swisstokint:pom-rx-exact-authorization:v1:") ||
  UTF8(canonical_exact_authorization_binding)
)
```

Both canonical forms must use one explicitly reviewed deterministic canonicalizer; no platform locale, pretty-printing or object insertion order may affect the commitment.

## Capability identifier and lifetime

The local reference capability ID is generated by the trusted issuer as 128 bits of cryptographically secure randomness and encoded as:

```text
cap-<32 lowercase hex>
```

The first Core profile permits a lifetime from 1 second through 5 minutes. Applications may tighten this maximum but may not widen it without a new reviewed profile. `expires_at` must be later than `issued_at` and must never exceed the bound witness validity window used for issuance.

## Issuance boundary

No capability may be treated as authorization merely because it has the correct JSON shape or hashes.

A future production issuer must prove all of the following before minting a usable capability:

1. strict preflight structural verification succeeds under the exact selected verifier/policy/artifact tuple;
2. the preflight outcome is `allow`;
3. a distinct enrolled source key and enrolled witness key are accepted under active trust policy;
4. the witness acknowledgement is `witnessed`, never `dry_run`;
5. the witness acknowledgement binds the same preflight receipt hash/run and is unexpired at a trusted evaluation instant;
6. source or witness revocation effective at that instant fails closed;
7. source/witness key IDs match the exact signed evidence;
8. action/context/policy commitments match the intended execution binding exactly;
9. capability expiry is no later than the witness validity bound.

Until enrollment, revocation and trusted-time evidence exist, production issuance remains `UNPROVED`.

## Capability representation

For the first local reference runtime, the usable capability must be process-local, branded and non-serializable. A plain parsed object, clone or reconstructed record cannot impersonate it.

The untrusted application/dApp never receives the capability object. A future cross-process capability format is a separate design problem and must not be inferred from the local reference model.

## Gate bootstrap boundary

The Gate is constructed at a trusted bootstrap boundary with private references to:

```text
trusted_clock
observe_binding
execute_downstream
```

- `trusted_clock` returns the trusted evaluation instant and is not supplied per request;
- `observe_binding` is an application-owned trusted adapter that derives the current `binding_profile`, `action_commitment` and freshly observed `context_commitment` from the execution attempt and trusted environment;
- `execute_downstream` is the only downstream execution/provider reference in the accepted harness.

The caller receives only the Gate handle. It does **not** supply an `execute_once` callback, a trusted timestamp, origin, chain/account state or a precomputed trusted context commitment at consumption time. This prevents the caller from bypassing the Gate or self-attesting the context being checked.

## Gate state machine

The Gate owns the only reference to the downstream execution adapter in the accepted harness.

Terminal state machine:

```text
AVAILABLE
  -> VALIDATING   # capability reserved synchronously before any async observation
       -> REJECTED
       -> CONSUMING
            -> CONSUMED_SUCCESS
            -> CONSUMED_ERROR
```

Rules:

- a branded capability leaves `AVAILABLE` synchronously before any `await`, context observation or downstream call;
- a second concurrent attempt therefore cannot reserve the same capability;
- `REJECTED`, `CONSUMED_SUCCESS` and `CONSUMED_ERROR` are terminal;
- observation error, malformed trusted observation, mismatch or expiry ends in `REJECTED` without downstream execution;
- the Gate checks expiry once after reservation and again immediately before forwarding so a capability cannot expire during asynchronous context sampling and still execute;
- an execution error never rearms a capability automatically;
- retry requires a new preflight/witness/authorization cycle;
- replay, concurrent reuse, expiry, action mutation or context mutation never call downstream execution;
- a failed consumption attempt may sacrifice availability to preserve fail-closed single-use semantics; availability is not a safety requirement.

## Trusted time

Capability expiry is evaluated only with the private `trusted_clock` configured at Gate bootstrap. Receipt time, request time, dApp metadata or caller-supplied timestamps cannot extend capability life.

For the local reference runtime the clock may be an explicitly injected host function for deterministic tests. Production time-source trust remains a separate deployment requirement.

## Exact comparison

The Gate compares exact normalized identifiers and lowercase SHA-256 commitments. No wildcard, range, fuzzy matching, case-insensitive semantic matching or fallback is permitted.

The trusted `observe_binding` adapter must freshly sample application context immediately before consumption. For Wallet Guard, dApp-supplied origin, chain, account or equivalent metadata is never authoritative.

## Downstream ownership

Only the Gate may hold/call the downstream provider or mutation adapter in the accepted test harness. The dApp/application caller receives no second direct reference and cannot submit its own execution callback through `consume()`.

This property must be demonstrable in the local reference harness before any Wallet Guard readiness claim.

## Reference implementation boundary

The first implementation lot may provide:

- strict validation of the exact authorization binding;
- deterministic domain-separated commitment helpers;
- a process-local branded **test/reference** capability;
- a Gate constructed with private clock/observer/downstream adapters;
- the terminal single-use state machine;
- concurrency/replay/mutation/expiry adversarial tests;
- a fake downstream adapter proving zero calls on rejected paths and one call on the allowed control path.

It must not claim production authorization because the production issuer trust prerequisites are still incomplete.

## Adversarial acceptance matrix

The reference Gate must prove at least:

1. plain-object capability injection — rejected;
2. cloned/reconstructed capability — rejected;
3. malformed capability — rejected;
4. expired capability at reservation — rejected without downstream call;
5. capability expires during async observation — rejected before downstream call;
6. action commitment mutation — rejected without downstream call;
7. context commitment mutation — rejected without downstream call;
8. binding-profile substitution — rejected;
9. preflight/policy/witness/verifier binding mutation — rejected;
10. replay after success — rejected;
11. replay after downstream error — rejected;
12. concurrent double consumption — only one reservation may proceed;
13. exact valid control — downstream called exactly once;
14. downstream error — capability remains terminal, no automatic retry;
15. caller cannot inject its own downstream callback or trusted timestamp/context;
16. test/reference issuer is not exposed as production authorization.

## Security blockers before production authorization

The following remain mandatory and separate:

- source/witness enrollment;
- source/witness revocation;
- trusted clock/time boundary;
- durable or multi-process replay/consumption storage if the Gate leaves one process;
- key rotation/compromise recovery;
- deployment/host integrity;
- application-specific normalization and fresh context observation;
- native execution evidence and reconciliation.

## Readiness labels

`CORE_GATE_REFERENCE_READY` means only that the local reference state machine and adversarial tests pass with a fake downstream adapter.

`CORE_EXACT_AUTHORIZATION_READY` additionally requires the production issuer trust prerequisites above. The reference Gate alone cannot earn this label.

Neither label means production readiness, wallet safety, financial safety, audit or certification.

## Proposed implementation sequence

1. SpecKit + architecture/security review of this council/ADR.
2. Reference exact-binding validator and branded test capability.
3. Single-use local Gate state machine and adversarial tests.
4. Witness enrollment/revocation/trusted-time hardening.
5. Production issuer integration.
6. Wallet Guard application adapter and simulated E2E.
7. Burner-wallet local/testnet E2E only after a separate human gate.

## Human gates

Human approval is required before:

- merging this Core Gate contract;
- activating a production issuer;
- exposing a production authorization capability;
- connecting a real wallet/provider or performing a testnet/mainnet transaction;
- changing Gate state transitions, binding semantics or replay rules after ratification.
